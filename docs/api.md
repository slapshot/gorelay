# HTTP API contract (v0.1 proposal)

**Design only.** These routes are not currently running.

## Network and request rules

Default binding: 127.0.0.1 on an explicitly configured port. All versioned endpoints require an authenticated client except health/readiness. Protect health/readiness by network binding, not by assuming they contain no useful information.

Requests are JSON over HTTP/1.1 or HTTP/2; UTF-8 only; no trailing JSON tokens; reject duplicate JSON object member names to prevent validation ambiguity. Maximum request body size **256 KiB by default**, measured before decoding, with a configured hard upper bound. Reject content encodings not explicitly implemented. Use strict envelope fields, while payload remains application-defined JSON. Initial payload type: JSON object.

Headers:
- Authorization: Bearer <opaque client credential>; mapped to a server-side client identity.
- Idempotency-Key: required, 1–200 printable ASCII characters, without controls.
- Content-Type: application/json.
- X-Request-ID: optional diagnostic value, validated and size-limited; server generates an ID if absent.

The client identity must **never** be inferred from the body. Rate limits and authorization are scoped to the authenticated client.

## POST /v1/events

Request example:

    POST /v1/events HTTP/1.1
    Authorization: Bearer <credential>
    Idempotency-Key: order-123-created
    Content-Type: application/json

    {
      "type": "order.created",
      "destination_id": "accounting-service",
      "payload": {"order_id":"123","amount":99.50,"currency":"EUR"}
    }

Validation:
- type: lower-case event name matching ^[a-z][a-z0-9_.-]{0,127}$.
- destination_id: ^[a-z][a-z0-9_-]{0,63}$ and configured for this client.
- payload: valid JSON object, bounded by total request cap.
- idempotency key is required, unique per client for the lifetime of its record.
- no arbitrary destination URLs, secrets, event IDs or source identity in the request.

New event: HTTP **202 Accepted**, returned only after transaction commit:

    {
      "id": "7f3b8ad0-812a-4fc1-bc02-c2ba2472bce1",
      "status": "PENDING",
      "created_at": "2026-11-05T09:00:00Z"
    }

Duplicate idempotency key with same normalized request content: **200 OK** with original event ID and its **current** status. Same key with different request fingerprint: **409 Conflict**. Concurrent attempts must be resolved by the database unique constraint, never by check-then-insert.

Fingerprint input: canonical deterministic encoding of validated fields type, destination_id, and payload (not authorization headers, idempotency key, client-provided whitespace, request IDs or server timestamps), hashed with SHA-256. v0.1 pre-alpha rule: number spelling is significant (1 and 1.0 differ); only JSON object key ordering and whitespace are normalized. Review this rule before stable release. Preserve JSON numbers rather than silently converting all of them to float64. The key's unique scope is (client_id, idempotency_key).

## GET /v1/events/{id}

200 OK to the authenticated owning client:

    {
      "id": "7f3b8ad0-812a-4fc1-bc02-c2ba2472bce1",
      "type": "order.created",
      "destination_id": "accounting-service",
      "status": "RETRY_WAIT",
      "attempts": 2,
      "next_attempt_at": "2026-11-05T09:02:00Z",
      "created_at": "2026-11-05T09:00:00Z",
      "delivered_at": null
    }

Do not include payload, credentials, destination secret, raw response bodies, or stack traces. Do not permit client A to read client B's status. Return 404 for a nonexistent or unauthorized ID to limit enumeration.

## GET /healthz and GET /readyz

healthz returns 200 when the process can answer (liveness; does not require PostgreSQL).

readyz returns 200 only if the service has completed startup validation, can perform a bounded database readiness query, and is not shutting down. A dependency failure returns 503. Readiness must have a short timeout and must not emit sensitive details.

## Status and errors

| Condition | HTTP status |
| --- | --- |
| Durable acceptance | 202 |
| Idempotent duplicate | 200 |
| State query success | 200 |
| Malformed input / JSON | 400 |
| Missing or invalid authentication | 401 |
| Valid credential but unauthorized destination | 403 |
| Unknown/unowned event | 404 |
| Idempotency key reused for different content | 409 |
| Unsupported content type | 415 |
| Request over configured limit | 413 |
| Client quota exceeded | 429 with Retry-After |
| Dependency unavailable / draining | 503 |
| Unexpected server failure | 500 |

Error envelope:

    {"error":{"code":"IDEMPOTENCY_CONFLICT","message":"Idempotency key already used for a different request","request_id":"..."}}

Stable machine-readable error.code; no stack traces or internal paths. Document every error and test response headers. Return Cache-Control: no-store for authenticated API responses.

## Protocol and compatibility

- All timestamps RFC 3339 UTC.
- IDs are UUIDs generated by the service (implementation must not rely on sortable UUIDs).
- No ordering guarantee across distinct events.
- Explicit API version in route. Backward-compatible fields can be added; clients must ignore unknown response fields.
- A success response is **not** a promise of remote processing or immediate delivery.
- No POST retry without stable Idempotency-Key if the response is ambiguous.
- On load shedding, the service must reject before acknowledging durable admission.
- Durable idempotency lasts as long as event records are retained. A future purge policy may end that guarantee; document and test it first.

## Outbound HTTP contract

Delivered with POST application/json and an envelope:

    {
      "id":"7f3b8ad0-812a-4fc1-bc02-c2ba2472bce1",
      "type":"order.created",
      "source":"example-client",
      "payload":{"order_id":"123","amount":99.50,"currency":"EUR"},
      "created_at":"2026-11-05T09:00:00Z"
    }

Headers: X-GoRelay-Event-ID, X-GoRelay-Attempt, X-GoRelay-Timestamp, X-GoRelay-Signature (v1=<lowercase hex HMAC>), Content-Type. Signature v1 signs UTF-8 timestamp + "." + the exact outbound body bytes with destination-specific HMAC-SHA256 key. A receiver verifies the timestamp freshness window, signature in constant time, and persistent event-ID deduplication. Every retry can have a new timestamp/signature but reuses the same event ID.

2xx counts as delivered; redirects are not followed. Full response status policy: [workers.md](workers.md).

A machine-readable OpenAPI 3.1 document will be added and validated after this written contract is reviewed.
